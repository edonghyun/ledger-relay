# 설계 요약

ledger-relay가 무엇을 보장하고, 그 보장을 어떤 개념으로 지키는지 한 쪽에 모았다. 코드와 테스트의 `G1`~`G7`은 아래 보장을 가리키고, `F1`~는 [failure-modes.md](failure-modes.md)의 막은 장애를 가리킨다.

## 문제

PostgreSQL(PG)에 업무 데이터를 두고 TigerBeetle(TB)에 돈의 이동을 기록하는 앱은 둘을 한 트랜잭션으로 묶을 수 없다. 게다가:

- TB 클라이언트에는 timeout이 없고, 응답은 유실될 수 있다. 보냈는지 아닌지 모르는 순간이 생긴다.
- TB에서 일시적 실패로 끝난 이체 ID는 다시 쓸 수 없다(`id_already_failed`).
- 확정(post)이 예약(reserve)보다 먼저 도착하면 확정이 실패하고 그 ID가 소진된다.

일반 Outbox는 "전달 성공"을 기준으로 다음 메시지를 보낸다. ledger-relay는 **원장 결과**를 기준으로 다음 명령을 보낼지, 기다릴지, 건너뛸지 정한다.

## 보장

| | 보장 | 지키는 방법 |
|---|---|---|
| **G1** | 접수의 원자성. 앱 트랜잭션이 커밋되면 명령도 저장되고, 롤백되면 명령도 사라지며 TB에도 영향이 없다. | 명령을 앱과 같은 PG 트랜잭션에 저장한다. 트랜잭션 없이 `submit()`을 부르면 예외를 던진다. |
| **G2** | 같은 순서 키의 뒤 명령은 앞 명령이 최종 상태가 되기 전에는 제출하지 않는다. 결과가 미확정인 동안 재시도해도 이중 반영이 생기지 않는다. | 명령 1개가 최대 1회 반영되는 것은 TB의 이체 ID 멱등성이다. ledger-relay는 그것을 재시도 흐름까지 넓힌다. |
| **G3** | 접수된 명령은 최종 상태(APPLIED, REJECTED, CONFLICT, SKIPPED)에 도달한다. 도달하지 못한 명령은 상태 조회와 운영자 포트에 계속 드러나고 조용히 사라지지 않는다. | lease가 끝나면 다른 워커가 같은 이체 ID로 다시 보낸다. 멈춘(HALTED) 명령은 운영자가 본다. |
| **G4** | 순서 키 안의 순서. 다음 명령은 같은 키에서 순번이 더 작은 명령이 모두 최종 상태일 때만 제출한다. 확정·해제가 참조한 예약이 APPLIED가 아닌 최종 상태면 그 명령은 SKIPPED로 끝난다. | 키마다 순번을 주는 행을 잠가 순번 순서가 커밋 순서와 같다. 키마다 "맨 앞" 명령 하나만 claim 후보가 된다. |
| **G5** | 상태는 앞으로만 진행한다. 현재 lease를 쥔 워커만 상태를 바꿀 수 있고, 최종 상태는 다시 바뀌지 않는다. | lease 토큰을 조건으로 건 UPDATE(fencing). |
| **G6** | 결과 반영 핸들러의 DB 변경은 명령의 최종 전이와 같은 트랜잭션에서 커밋된다. 커밋되는 핸들러 효과는 최종 전이 1회당 정확히 1회다. | 핸들러 코드는 여러 번 실행될 수 있다(롤백 뒤 재시도). 외부 부작용은 커밋 뒤 이벤트로 넘긴다. |
| **G7** | 내용 무결성. 같은 `commandId`로 다른 내용을 접수하면 `CommandConflictException`을 던진다. TB가 `exists_with_different_*`를 돌려주면 성공으로 처리하지 않고 CONFLICT로 남긴다. | 정규화한 내용 해시로 비교한다. |

## 개념

- **명령**(`LedgerCommand`): TB 이체 하나. 종류는 단순 이체(transfer), 예약(reserve, TB의 pending), 확정(post), 해제(void)다. 명령 하나에 TB 이체 ID 하나가 대응한다.
- **순서 키와 순번**: 순서가 중요한 명령(예: 한 주문의 예약 → 확정)은 같은 순서 키로 접수한다. 키마다 순번이 1부터 늘어난다. 다른 키끼리는 서로 기다리지 않는다.
- **맨 앞**: 키마다 아직 끝나지 않은 명령 중 순번이 가장 작은 것. 워커는 맨 앞 명령만 잡는다(F1, F32).
- **lease**: 워커가 명령을 잡은 기한. 기한 안에 결과를 쓰지 못하면 다른 워커가 같은 이체 ID로 다시 보낸다. TB가 `exists`로 답하므로 돈은 두 번 움직이지 않는다.
- **결과 분류**: TB의 결과 코드 68개를 적용됨, 업무 거절, 충돌 등으로 나눈다. 일시적 실패는 재시도하고, 같은 ID로는 다시 보낼 수 없는 결과는 그대로 최종 상태로 남긴다.
- **멈춤(HALTED)**: 접수 검사를 거치지 않은 행(버그, DB 직접 수정)처럼 판단할 수 없는 명령은 그 키만 막고 멈춘다. 운영자 포트(`LedgerRelayOperator`)로 보고 포기한다.
- **대사**: 끝난 명령마다 PG의 결과와 TB의 이체가 맞는지 확인한다(`LedgerRelayOperator.reconcile`).

## 모듈

```
ledger-relay-core          규칙(상태 전이표, 결과 분류, 순서 게이트)과 서비스. JDK만 쓴다
   ↑            ↑
ledger-relay-jdbc   ledger-relay-tigerbeetle     저장소(PostgreSQL)와 원장(TB) 어댑터
   ↑            ↑
ledger-relay-spring-boot     자동 설정, 워커 루프, health
   ↑
examples/shop              라이브러리를 쓰는 샘플 앱
```

의존 방향은 ArchUnit 테스트가 지킨다. 업무 판단은 core에만 있고, 어댑터는 조립과 입출력만 한다.
